Overview

DCL evaluates AI-agent actions against a security policy and records each decision as an audit event. This Board publishes those records and the payment data attached to them. It shows what DCL exported; it does not verify the records itself.

What each metric counts

Audit Events
Rows in each service's audit chain (Trust Oracle, Bazaar) plus Sentinel events. Canonical events produced by integration demos (Shasta, Tenjin) come from outside those databases and are not included.
Recorded Payments (USDC)
Sum of the payment amounts attached to COMMIT audits for Trust Oracle and Bazaar, plus all Sentinel payments. Payments attached to audits whose verdict is not COMMIT are not included. Amounts are as recorded by each service; this Board does not check them against the chain.
Not COMMIT
The export's no_commit_count. In the exporter source it is calculated as total audits minus COMMIT audits, so it counts every verdict other than COMMIT. Only the row-level events below show the actual verdict value of each audit; Technical details lists the values seen.
Paid Verifications
Not shown. The export does not link every audit to a settled payment, so a count would not be reliable.
On-chain Executions
Not implemented. No execution evidence exists yet.

Verification architecture

DCL connects a paid security evaluation to a recorded decision. The target design adds a signed authorization and an enforcement contract. Only the first three steps run today.

  1. An AI agent requests a security evaluation.Recorded
  2. The request is paid through x402. Amount and settlement reference are recorded where the export carries them.Recorded
  3. The DCL Trust Oracle evaluates the action and records COMMIT or NO_COMMIT as an audit event (DCL Audit Event v1.0).Recorded
  4. An approved decision produces a signed, narrowly scoped Proof of Allowance.Planned
  5. A guarded smart contract verifies the allowance before running the protected action. Base is the intended first EVM environment.Planned
  6. The execution result is linked to its decision and payment evidence.Planned

How evidence is labelled

One status never stands in for the whole lifecycle. A recorded decision can exist without a verified payment, and a payment can exist without any allowance.

StatusMeaningOn this Board today
RecordedDCL stored the record and exported it.Shown for every event.
Cryptographically verifiedA hash or signature was recomputed and matched.Not shown. The Board does not recompute hashes or signatures.
Payment confirmedSettlement was checked against the chain.Not shown. References are displayed with a block-explorer link; the Board does not check them.
Allowance signature verifiedA Proof of Allowance signature was verified.Not implemented.
Execution confirmedA guarded contract executed the action on-chain.Not implemented.
RejectedThe evaluation returned NO_COMMIT.Shown as NO_COMMIT, with the reason when exported.
Unavailable / Not implementedA data source or feature does not exist yet.Shown instead of a zero or a placeholder value.

Two different hashes

DCL audit hash
The proof.tx_hash field. A local hash of the audit record, computed by DCL. It is not a blockchain transaction and cannot be looked up on a chain.
Settlement transaction
The payment.tx_hash field. The on-chain transaction that settled an x402 payment. For Base it can be inspected on a block explorer.
